# M6 Admin Roles and Inline Control Panel

Migration `0006_admins.sql` creates the durable `admins` role table. At application startup, validated `ADMIN_IDS` from the environment are inserted idempotently into that table. Existing database-only admins are preserved. Authorization checks environment IDs first (the protected super-admin fallback), then the database role registry. If the database lookup fails, configured environment admins remain authorized.

## Open the panel

An administrator can send `/admin` or `/panel` in a private chat. Each explicit command opens a fresh control-panel message; the previous panel is retired and its callbacks become invalid. Within the active panel, categories, requirements, staff lists, confirmations, settings, and Add-flow responses replace the text and inline keyboard of that exact message. The panel binds callbacks to its owner, private chat, message ID, and a per-panel nonce; callbacks from another user or an old message are rejected. If an edit fails, the bot sends a clearly labelled replacement panel and invalidates the old message rather than silently leaving an unusable panel.

The main menu provides **Categories**, **Requirements**, **Staff**, and **Settings**:

- **Categories:** paginated category list, **Add Category**, category details, parent/child links, and deletion with an explicit choice about orphaned requirements. Add Category asks for a name and then a forwarded storage-channel message or numeric chat ID; the bot reminds the admin that it needs posting permission. Deletion warns that items and stored media remain and move to `Default`, while all share links for those items are revoked. Parent/child links to the deleted category are removed, but linked category records and storage channels remain, even when the storage channel is shared. The admin chooses whether to keep or delete requirements that become orphaned. `Default` is protected from deletion.
- **Requirements:** global and category scopes, rules directly attached to each scope, and a button-driven Add Rule wizard. When a rule is shared across scopes, removal offers **Unlink Here** or **Delete Everywhere**; a rule used by only one scope is removed directly.
- **Staff:** separate **Add Admin** and **Add Uploader** actions, lists of database/environment administrators and active uploaders, and removal controls. Environment super-admins cannot be revoked. An admin's uploader access cannot be revoked from this UI.
- **Settings:** lock/unlock regular-user commands and uploads, and choose the policy for unavailable Real JOIN_CHAT/REACT checks. The persisted `REAL_CHECK_FAILURE_POLICY` defaults to **Fail closed**: deny delivery without consuming the share-link use. Admins may instead select **Configured wait fallback**, which waits the rule's configured duration and then allows the usual delivery flow. The UI describes the consequence and audits policy changes. Navigation is kept simple so future settings can be added without introducing a broad permission matrix, which remains out of scope.

## Rule creation wizard

Rule creation uses inline buttons for the requirement type (`JOIN_CHAT`, `REACT`, `START_BOT`, or `TIMED_WAIT`), Real/Fake handling (where supported), optional prompt link, wait time, REACT windows, and final confirmation. `TIMED_WAIT` skips target selection. For `JOIN_CHAT` and `REACT`, forward a message from the target channel/group or paste its numeric chat ID; for `START_BOT`, forward a user's message or paste the numeric user ID. Public usernames in forwarded messages automatically supply a `t.me` link; for private targets, the admin may paste an invite URL. The optional URL must use HTTPS on `t.me` or `telegram.me`. Typed rule syntax and target usernames are not accepted. Every wizard screen has **Cancel**.

Wait choices are 0, 3, 5, 10, 30, and 60 seconds. REACT message choices are no message limit, 3, 5, or 10 posts; age choices are 0, 7, or 30 days. The two bounds can be disabled independently: a zero message bound means any observed post can qualify, but a reaction is still required; zero days disables the age cutoff. Real REACT passes when the user has at least one tracked reaction in the selected window. The bot must have channel-admin access and must have observed the post/reaction updates. If a Real check is unavailable, the persisted admin policy determines whether delivery is denied without spending a link use (default) or the configured wait fallback is used. Real `START_BOT` verification is unsupported without a separate attestation bridge, so the wizard offers only Fake prompt-and-wait mode for that type. `TIMED_WAIT` has no Real/Fake selector because it is always wait-only.

Fake JOIN_CHAT, REACT, and START_BOT rules show a generic user-facing instruction and, when configured, a URL button before passing immediately or after the selected wait. Real JOIN_CHAT/REACT denials also show the configured link button when available. Opening or clicking a link is **not** treated as proof of joining, starting a bot, or reacting; the Fake path is an explicitly configurable prompt/wait pass, while Real checks continue to use membership or recorded reaction state.

When **Real** is selected for `JOIN_CHAT`, the panel checks whether the bot is an administrator in the target chat. If Telegram confirms it is not an administrator, the panel warns the admin. If lookup is unavailable, it does not misrepresent that as a confirmed non-admin result. The admin can continue or switch to Fake.

## Add-flow state machine and timeout

The panel stores a small state record in the administrator's `context.user_data`: panel owner, nonce, chat/message IDs, current view, pagination/scope, and any pending input or rule-wizard data. Category creation asks for a category name, then accepts a numeric storage-chat ID or a forwarded channel/chat message. Staff flows accept a numeric user ID or a forwarded user message. Rule target prompts accept a numeric ID or a forwarded channel/group/user message. The optional prompt-link step accepts only a Telegram HTTPS URL. Rule syntax and typed target usernames are not accepted in the panel.

Pending staff, category, or rule-wizard state expires after five minutes of inactivity. On the next relevant interaction—including a command—the expired state is cleared and the panel resets to its Main Menu; an expired text message is not consumed as wizard input. Completing or cancelling a flow also clears its pending state. Valid clicks and prompt/results continue to edit the active panel message rather than sending new messages.

## Command and upload lockdown

When `ENABLE_USER_COMMANDS=false`, regular users are blocked from commands except `/start`, as well as from uploading media. `/redeem` is locked too; admin-managed allowlisting remains available through Staff. Environment admins, database admins, and active uploaders bypass the lock. The lock does not grant upload permission by itself; normal uploader authorization still applies to upload processing.

## Verification and tests

M6 tests mock Telegram calls; no live Telegram API interaction is performed by the test suite. The M5 rules engine is exercised through mocked `/start <token>` flows covering a five-second Fake JOIN prompt/link, immediate zero-wait Fake JOIN, Real JOIN_CHAT refusal without consuming a share-link use, configurable fail-closed versus wait-fallback behavior for Real JOIN_CHAT and REACT, zero-second Fake TIMED_WAIT, and Real REACT with and without a stored reaction. Category deletion tests verify that affected share links are revoked while stored items, shared storage destinations, and other-category links remain. The tests also cover prompt-link validation, links on Real denials, database-admin lockdown bypass, settings persistence, and Add Uploader persistence within the single panel message.
