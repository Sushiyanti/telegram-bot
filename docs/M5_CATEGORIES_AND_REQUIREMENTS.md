# M5 categories and dynamic requirements

M5 adds category-specific storage destinations and requirements checked before a share link is consumed. The current database schema is version 6. Migration `0005_dynamic_rules_categories.sql` creates the protected `Default` category, assigns existing items to it, and backfills each item's original storage-channel ID from its message references. Migration 0006 adds database-backed admins. Existing item and storage-message records are retained when a category is deleted.

## Admin commands

All commands below are private-chat, admin-only commands and use the existing authorization and audit handling.

- `/addcategory <name> <channel_id>` creates a category and selects the numeric Telegram channel ID where new uploads in that category are stored. Names are supplied as one command argument; `Default` and `Global` are reserved.
- `/linkcategory <parent_name> <child_name>` makes the child category's requirements apply to items in the parent category as well. Links can be nested, but cycles are rejected.
- `/addrequirement <category_name|global> <type> <target> <is_fake> <wait_seconds> [last_x_messages last_x_days]` adds a rule to one category or globally. Supported types are `JOIN_CHAT`, `REACT`, `START_BOT`, and `TIMED_WAIT`. `JOIN_CHAT` and `REACT` require a numeric chat ID; fake `START_BOT` accepts an `@username`; `TIMED_WAIT` uses `-` as its target. `is_fake` must be `true` or `false`; waits are bounded to 0–86,400 seconds. The two optional window arguments are REACT-only; message counts are bounded to 0–1,000 and days to 0–36,500.
- `/delcategory <name>` presents an inline confirmation to cancel, delete requirements that become orphaned, or keep them. On confirmation, active share links for items assigned to that category are revoked; item/media records remain and items and pending uploads are reassigned to `Default`. Category graph links to the deleted category are removed, but other linked categories and storage channels remain, including channels shared by multiple categories. `Default` itself cannot be deleted.
- `/togglecommands` flips and persists the regular-user command/upload lock. When locked, regular users may use only `/start`; other commands (including `/redeem`) and media uploads are stopped. Environment/database admins and active uploaders bypass the lock.

The `Default` category is created during initialization and receives the configured `STORAGE_CHANNEL_ID` if it does not already have a storage destination. If it is the only category, uploads continue to use it automatically. With multiple categories, the uploader must choose a destination from an inline keyboard before the bot copies anything. The pending upload and selection state survive restarts. Selection callbacks are bounded in size and accepted only from the user who submitted the pending upload.

The bot validates that each category has a non-zero numeric channel ID, but it does not verify channel membership or posting rights when a category is created. Add the bot as an administrator with posting permission in every configured storage channel before using that category.

## Rule behavior and Telegram limitations

Global rules apply to every category. A category inherits rules from all descendants linked beneath it, in addition to its own rules and global rules. A denied requirement leaves the share-link use count unchanged. Fake `JOIN_CHAT`, `REACT`, and `START_BOT` requirements skip the Telegram check, show a generic instruction and optional Telegram URL button, then pass immediately or after `wait_seconds`. A clicked/opened URL is not verification. `TIMED_WAIT` sends `Please wait...`, waits for `wait_seconds`, and passes.

Real `START_BOT` verification is not supported by the Bot API: a bot cannot query whether someone started another bot. Creation of a non-fake `START_BOT` rule is rejected with `Real START_BOT verification is not supported yet, please use is_fake=True`. The [Telegram Bot FAQ](https://core.telegram.org/bots/faq) describes the visibility limits that prevent this check.

Real `JOIN_CHAT` rules use `getChatMember`. A user who is not a member is denied with a join instruction and, when configured, an optional Telegram URL button. For check failures or unavailability, admins choose the persisted `REAL_CHECK_FAILURE_POLICY` in the panel Settings. It defaults to `fail_closed`: delivery is refused and the share-link use is not consumed. Admins may choose `wait_fallback`, which waits for that rule's configured duration and then continues delivery. The wait fallback is not proof that membership was verified.

Real `REACT` rules default to at least one reaction on one of the latest five eligible posts (`last_x_messages=5`, `last_x_days=0`). For example, `last_x_messages=10` and `last_x_days=30` require a reaction on at least one of the latest 10 eligible posts published within the last 30 days. A message limit of zero means any observed post can qualify; it does **not** disable the reaction requirement. `last_x_days=0` disables the age cutoff. The bot stores observed channel posts and identifiable users' current reactions, and replaces/removes those records as reaction updates arrive. Verification requires the bot to be an administrator and requires `message_reaction` updates to be requested. If the Real check or its required state is unavailable, the same admin-selected `REAL_CHECK_FAILURE_POLICY` applies: fail closed by default without consuming the share-link use, or use the rule's configured wait as an explicit fallback. If the check is available but the user has no qualifying reaction, delivery is denied with an optional Telegram URL button when configured.

Reaction state is not backfilled. The Bot API does not provide a general method to retrieve historical channel posts and per-user reaction state, so only posts and reaction changes observed by the running bot are available for verification. Have the bot as an administrator and receiving updates before relying on reaction checks. See the [Bot API](https://core.telegram.org/bots/api) and [python-telegram-bot Update documentation](https://docs.python-telegram-bot.org/en/v22.8/telegram.update.html) for the admin and allowed-update requirements.

No live Telegram checks are part of the automated suite. Tests mock Telegram interactions; a provisioned bot, channels, and authorized test users are required for live integration verification.
